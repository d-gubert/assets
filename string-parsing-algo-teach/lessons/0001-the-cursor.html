Lesson 01 · String Parsing

The Cursor

Every parser you will ever hand-write is one integer and three questions. Today you write your first one, and it parses a real piece of the tmux line.

1: Tab #1* (3 panes) [382x99] [layout 66e3,382x99,0,0{127x99,0,0,0,127x99,128,0,2,126x99,256,0,1}] @0 (active)

That is the string from your mission. By the end of this lesson you will have written the code that turns the bold part — 382x99 — into { w: 382, h: 99 }, with no libraries and no regex. It is a small piece. It is also the piece that appears four times in that one line, and every other lesson in this workspace is built on the machinery you write here.

1. Why split() is not a parser

You already know this feeling, so one demonstration is enough. Here is the obvious way to pull the window name out of the line:

// "1: Tab #1* (3 panes) [382x99] ..."
line.split(" ")  // → ["1:", "Tab", "#1*", "(3", "panes)", "[382x99]", ...]

The name is Tab #1. It contains a space. The delimiter you split on lives inside the field you were trying to extract, so the split destroys exactly the information you wanted. You can patch it — rejoin indices 1 through n, count backwards from ( — and each patch is a new assumption about a string you do not control.

The rule: split() is only safe when no field can ever contain the delimiter. The moment a format allows that — spaces in names, commas in nested lists, brackets inside brackets — splitting is guessing.

This is not a JavaScript problem. The same trap is why CSV is hard, why parsing HTML with string matching famously fails, and why IFS in shell scripts bites everyone eventually.

The alternative is not a cleverer split. It is to stop looking at the string as a whole and start walking it, one character at a time, deciding as you go.

2. The cursor

A cursor is two things: the source string, and an index into it. That is the entire state. Everything else is a function of those two values.

const src = "382x99";
let   pos = 0;   // ← the only thing that ever changes

From that state you get three primitives. Learn these three names; they are the same three names used in Robert Nystrom's scanner, and they will not change for the rest of this workspace.

// Look at the current character. Do NOT move.
function peek() {
  return pos < src.length ? src[pos] : "\0";
}

// Return the current character AND move past it.
function advance() {
  return src[pos++];
}

// Is there anything left?
function atEnd() {
  return pos >= src.length;
}

Why does peek() return "\0" past the end instead of throwing? Because it is called constantly inside loop conditions. A sentinel that compares unequal to every real character lets while (isDigit(peek())) terminate naturally at the end of input, with no bounds check written by hand. Nystrom makes the same choice.

The distinction between peek and advance is the whole idea, and it is the thing beginners get wrong. Peek asks. Advance commits. You peek to decide what to do; you advance once you have decided. Every parser you write from here is a loop of: peek, decide, advance.

Drive one yourself

Press the buttons. Watch which calls move the marker and which do not. Predict the return value before you click — that prediction is the point.

3. One derived helper: reading a number

With those three primitives, everything else is composition. To read a number you remember where you started, consume digits while there are digits, and slice out what you covered:

const isDigit = (c) => c >= "0" && c <= "9";

function readNumber() {
  const start = pos;
  while (isDigit(peek())) advance();
  return Number(src.slice(start, pos));
}

Read that loop carefully, because its shape recurs forever: peek to test, advance to consume. It handles 1, 382 and 18446744 identically, and it stops the instant it meets something that is not a digit — leaving pos sitting exactly on that character, ready for whoever asks next. Nothing was thrown away. Nothing was guessed.

The transferable idea

A parsing function's contract is: start at the first character of the thing you parse; return the value; leave pos on the first character you did not consume. Hold every function you write to that contract and they compose without you having to think about it.

4. Your turn

Write parseDims. It takes "382x99" and returns { w: 382, h: 99 }. The three primitives are given; the logic is yours. split, indexOf, match, replace and RegExp are blocked — that constraint is the lesson.

Task: parse a tmux dimension pair WIDTHxHEIGHT into { w, h }. Both must be numbers, not strings.

function parseDims(src) {
  let pos = 0;

  const peek    = () => pos < src.length ? src[pos] : "\0";
  const advance = () => src[pos++];
  const isDigit = (c) => c >= "0" && c <= "9";

  function readNumber() {
    const start = pos;
    while (isDigit(peek())) advance();
    return Number(src.slice(start, pos));
  }

  const w = readNumber();
  advance();                // step over the "x"
  const h = readNumber();
  return { w, h };
}

Notice the weak spot: that bare advance() consumes whatever is there, x or not. parseDims("382y99") happily returns {w: 382, h: 99}. Fixing that honestly is Lesson 2.

5. Retrieval check

Answer from memory, not by scrolling up. Getting one wrong here is more useful than getting all three right by looking.

You call peek() twice in a row. What do you get?

  • Both return the same character and the position stays put.
  • Both return the same character but the position moves once.
  • Each returns a different character because the position moves along.

When is split(delimiter) actually a safe way to parse?

  • No field may ever contain the delimiter used to separate fields.
  • Every field is quoted, so the delimiter never appears unescaped.
  • Every field must be the same length so offsets are known.

What should peek() do when pos is past the last character?

  • Return a sentinel value rather than throw, so callers can test it.
  • Throw an error immediately, since reading past the end is a bug.
  • Wrap back around to index zero so the scan can continue.
